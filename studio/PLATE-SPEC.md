## 2. 硬阈值

| 指标 | 必须落在 | 为什么 |
|---|---|---|
| 屏外（房间）平均亮度 | 77 ~ 192 | 曝光系数 = 房间目标亮度 / 实测亮度，要落在 0.55~1.40 |
| 屏幕占全帧面积 | 9% ~ 18% | <9% 房间补不回来（暗页帧跌破 94）；>18% 暗主题屏太大 |
| 屏幕宽（1080p） | ≥ 480 px | 34px 画布字号 × (宽/1600) ≥ 10px |
| 物理屏幕比例 | 4:3 | 画布 1600×1200；比例不符时四角单应会自动把内容拉伸 |

曝光公式（`detect-screen.py` 内置）：

```
房间目标亮度 R = ((96 - 0.315) / 0.955 - 50·a) / (1 - a)     # a = 屏幕面积占比
exposure = R / 该板实测屏外亮度
```

## 4. 三个实测教训

### 4.1 提示词里的「夜晚」会毁掉亮度账
即梦收到「夜晚/夜景/虚化」会把**整个房间**压到 48~67，要补到房间目标亮度需要 1.6~2.3 倍曝光，
台灯和窗景全部爆掉。而现用的 `desk-night` 是 91.2 —— 同为夜景却亮一倍。
**可用方向：白天 / 黄昏 / 明亮室内 / 大面积窗户透光。暗调交给主题和压暗层。**

### 4.2 太小能裁大，太大裁不了
即梦无法精确控制平板在画面里的比例（16 张候选只有 4 张天然落在窗口内）。
裁掉四周等于放大屏幕，面积按裁剪倍率²增长；但特写（20%+）**修不了**，只能重新生成。
上采样倍率控制在 1.45 以内，超过就重新生成。

### 4.3 自动定位会认错亮区 —— **每张板必须先实渲一帧再提交**
`office-bright` 第一版就是这么翻车的：自动检测把**白墙**当成了屏幕，
渲出来内容悬在半空。改用 `--seed` 指定平板内一点后才发现真实屏幕只有 6.25% 面积，
再裁 1.30 倍才达标。

**规矩：`detect-screen.py` 的叠加图只能证明「找到一块像屏幕的区域」，
证明不了「找到的是屏幕」。唯一可靠的验证是渲一帧看内容贴不贴。**

## 5. 还没解决：特写机位
A 组 4 张特写屏占比 20.6~23.8%。在现有亮度判据下不可用——
要满足「暗页帧 ≥94」得把房间抬到 114（曝光 1.4~1.8）。
这不是板子的问题，是**判据为 9.4% 屏占比定的**。要用特写，
得连同 16:9 画布一起放宽「亮页 ≥110 / 暗页 ≥94」，别单独改。

## 4.4 特写机位：不是放宽判据，是限制它能配的主题

特写屏占比 **22.29%**，是其它环境的 1.5~2.4 倍。这带来一个算术后果：

```
整帧 = (1 - a)·房间 + a·屏内
a = 0.2229 时：
  亮主题（屏内 225）→ 整帧 ≈ 117
  暗主题（屏内  50）→ 整帧 ≈ 77   ← 远低于「暗页帧 ≥94」
```

抬曝光救不回来：要托住暗页帧得到 94，房间亮度得压到 114，
此时亮页帧会冲到 137，整片平均直接出界。

**所以特写的解锁条件不是改判据，而是在注册表里写 `allowedThemes`：**

```json
{ "name": "closeup", "allowedThemes": ["light", "warm-sand"], "env": { ...,"exposure": 1.236 } }
```

规划器 `pickEnvironment()` 会先按主题过滤环境，再按版式偏好挑——顺序不能反。

配套两条：

- **曝光定标方式不同。** 普通环境按「暗页帧 → 96」定标（`detect-screen.py` 默认）；
  只配亮主题的环境要按「亮页帧 → 116」定标（加 `--light-only`）。
  用错定标会得到偏暗或偏亮 20 级的曝光。
- **特写占比建议 ≤1/3。** 单帧 117.9 已经在 105±12 的上沿；超过 1/3 的镜头是特写，
  整片平均会顶出 117。规划器现在按版式偏好轮换，实测约 1/5。

## 4.5 四角系统性内缩：检测器的通病，以及为什么最后用「放大」解决

2026-10-18 用户报：成片里 window-day 和 dusk-study 的镜头「画面四角和屏幕没对齐」，其余两块板正常。

### 现象与定量

把 quad 画回背景板、四角裁 2 倍放大后看：红线**整圈落在屏幕里面**，底部留了一条灰边。
`window-day` 的 BL 角偏了约 30~40px（1920 空间）。

### 试过但没用的两条路

1. **加大吸附半径。** 改成 ±90→±60→±36→±20→±10 分级吸附，五次全部 `ok`，
   但**收敛到的是同一条错的线**——说明梯度极值点本身就不在屏幕边缘
   （屏幕内侧有暗角和反光，梯度峰被拉进去了）。
2. **按「跨边界亮度台阶」逐边搜索**（`--optimize-edges`，1px 步长穷举）。
   它把四条边往**里**移了 30/17/4/6px，面积从 14.47% 掉到 13.10%，方向反了。
   原因：屏幕边缘有一圈更亮的反光边，屏内外的台阶在那一圈最大。

### 真正管用的：纯色探针 + 整体放大

用 `debug:"solid"` 把画布涂成品红，直接看它和屏幕的关系，一次就能读出「差多少」：

| 放大系数 | 结果 |
|---|---|
| 1.00 | 四边都有明显灰缝 |
| 1.03 | 缝变窄 |
| **1.06** | **正好贴到边框内侧** |
| 1.10 | 开始压到黑色边框 |

所以 window-day / dusk-study 的 quad 各放大 **1.06**（以质心为中心），
`desk-night` / `office-bright` / `closeup` 本来就是对的，不动。

### 结论（下次备板照做）

1. **别指望梯度吸附能校准到像素级。** 它能保证「找到了一块像屏幕的区域」，
   不能保证「这条线就是屏幕边缘」。
2. **纯色探针是唯一可靠的验收手段**：涂满品红渲一帧，人眼一看就知道差多少。
   比看内容准得多——内容有留白、有渐隐，肉眼判断不了边界。
3. **宁可轻微压住边框，也不要留灰缝。** 灰缝是「渲染坏了」，压一点边框只是「贴得紧」。
   实测 1.06 是这块板的甜点；换板子要重新试，一般落在 1.03~1.10。

## 4.6 真正的根因：占位屏是浅灰的（2026-10-18 第二次返工）

上一版（§4.5 的 1.06 放大）没解决问题。用户复看后仍报「那些镜头还是有问题」。

### 根因

逐块板比对后发现：**`desk-night` 的平板屏幕本身是黑的**（屏内亮度 14），
而另外四块板的屏幕是即梦生成的**浅灰占位**（屏内 138~176）。

于是同样一条缝：

| 环境 | 屏内亮度 | 缝隙露出来是什么 | 观感 |
|---|---|---|---|
| desk-night | 14（黑屏） | 深灰 | **看不出来** |
| window-day / dusk-study / office-bright / closeup | 138~176（浅灰） | 一弯亮灰 | **一眼就是没对齐** |

这解释了为什么用户只能说「有的对、有的不对」——他看到的其实全是同一类几何偏差，
只是浅灰屏那四块把它显影了。

### 为什么几何上贴不平

四边形是四条直线的交点，而设备屏幕的角是**圆弧**。任何盖到几何角的画布，
在角上必然多出/少掉一块，量是 `0.414 × r`。更麻烦的是**同一块板四个角的半径并不一致**
（实测 window-day：TL 58px、BL 73px；office-bright：TL 78px、BL 48px）——
即梦生成的板子本来就不是严格的圆角矩形，单一半径不可能同时贴合。

### 最终做法（三层，缺一不可）

1. **把占位屏涂暗**（`darken-screen.py`）：按亮区洪泛求出屏幕开口，向内腐蚀 2px，
   涂成 `#0a0c10`。从此任何缝隙露出来的都是边框色，不是亮灰。
   `desk-night` 因为本来就是暗屏，脚本会自动跳过。
2. **画布底下垫一层深色**（`ScreenLayer` 里 `fillRect` 整块）：圆角裁剪之外的残留也是暗的。
3. **quad 放大 1.03**：把「画布相对屏幕还差一点」补掉。有了前两层，放大过头也不会露白。

### 给下一次备板的硬要求

**提示词里要「屏幕显示纯黑色」，不要「纯中性灰色」。**
浅灰占位会把所有几何误差显影；黑屏把它们全部吸收掉。这一条比任何后处理都省事。

## 4.7 第三次返工：撤掉垫底、按「持续变暗」重拟合四边（2026-10-18）

用户反馈三条，全部对上：

1. **原本没问题的镜头四角出现黑色直角**
   → §4.6 里加的 `fillRect` 垫底层是**方角**，圆角裁剪在它里面，
     于是每个角都露出一个 90° 的深色尖角压在边框上。已删除。
     边缘露白继续由「涂暗背景板」解决（那是背景板自己的颜色，过渡自然）。

2. **之前有问题的镜头画面还是偏大**
   → 1.03 的放大过头。改成按拟合值重定位。

3. **镜6 的角度不对，画面边与屏幕边不平行**
   → 实测确认：`dusk-study` 的上边与屏幕边差 **4.12°**（拟合 RMS 0.35px）。
     594px 宽的屏，4° 就是横向走完差 40px，肉眼非常明显。

### 这一版为什么能量准

前几版都卡在判据上：

| 判据 | 为什么不行 |
|---|---|
| 梯度极值吸附 | 屏幕内侧有暗角/反光，极值不在边缘上 |
| 逐边最大化亮度台阶 | 偏向更亮的那圈反光 |
| 从外往里找「由暗转亮」 | 窗边那块板外侧是**亮窗**，一进窗口就是亮的，四条边全部卡在搜索边界 |

最终判据：**从屏内往外扫，第一段「连续 ≥7px 都在阈值以下」的起点就是屏幕边缘。**
对亮背景免疫，也不会被屏内细笔画文字骗到（要求连续暗）。

还有一个坑：**涂暗之后就没法量了**（屏内亮度 12，阈值失效）。
所以量测必须用**涂暗前的原图**（`snap-edges.py --orig-dir`，从 git 取回）。

### 实测结果（每条边的偏移与角度差）

| 环境 | 各边偏移 px | 各边角度差 | 角位移 |
|---|---|---|---|
| window-day | -34 / -26 / -8 / -8 | -0.54 / -0.12 / +0.03 / -0.01° | 10~40px |
| dusk-study | -21 / -9 / -5 / -8 | **+4.12** / -0.06 / -0.08 / +0.03° | 9~41px |
| office-bright | -23 / -44 / -19 / -34 | +0.65 / +0.55 / +0.39 / -0.34° | 33~57px |
| closeup | -1 / 0 / 0 / 0 | 可忽略 | 1px |
| desk-night | 无法量（暗屏） | — | 不动 |

拟合 RMS 全部在 0.33~1.10px，说明每条边确实是直线、拟合可信。

### 现在的状态
1 倍画面下四块板都贴合：没有亮缝、没有黑直角、上边与屏幕边平行。
2 倍放大看只剩 1~2px 的台阶（重采样锯齿），不是几何偏差。

后面三次返工全部是错的：

| 提交 | 改了什么 | 结果 |

| `3eb097a` | 涂暗占位屏 + 垫底 + 放大 1.03 | 四角出现黑色直角 |

### 为什么会一路做错：检查器的参照物错了

前面所有检查器的判据都是**相对自己**的，所以它们能全 PASS 而结果错：

| 检查器 | 参照物 | 为什么抓不到 |
|---|---|---|
| `check-canvas-overflow.py` | 内容 vs canvas | canvas 自己小了它查不出 |
| `check-film.py` | 帧 vs 帧 | 镜头内部的贴合不在视野 |
| `measure-fit.py`(第一版) | 「第一个暗像素」 | 占位屏涂暗后，找到的正是我自己画的画布——循环论证 |

### 新增：`check-fit.py`（掩码版，这一维之前完全缺失）

参照物换成**背景板里那块设备屏幕本身**，两个数同时对「太大」和「太小」敏感：

```
coverage = |canvas ∩ 屏幕开口| / |屏幕开口|     屏幕被盖住了多少   要求 ≥99%
overflow = |canvas \ 屏幕开口| / |屏幕开口|     画布有多少落在屏幕外 要求 ≤2%
```

实测（恢复后的基准）：

| 环境 | 覆盖率 | 溢出 | 屏内亮度 |
|---|---|---|---|
| window-day | 0.997 | 8.4% | 138 |
| dusk-study | 0.995 | 3.9% | 152 |
| office-bright | 1.000 | 29.1% | 153 |
| closeup | 0.997 | 0.5% | 176 |
| desk-night | — | — | 14（暗屏，跳过） |

覆盖率 99.5~100% 说明**屏幕被盖满了**；溢出量落在黑色边框上，所以看不见。
`office-bright` 的 29% 偏大，说明那块板的四边形比实际屏幕大了一圈（边框那侧看不出来），
如果要更精细可以单独收 2~3%。

### 硬规矩（写给下一次）

1. **改几何之前先渲一帧，和已知正确的图并排比。** 这次如果第一步就这么做，三次返工都不会发生。
2. **贴合的正确形态是「窄而均匀的亮边」，不是「边缘重合」。** 判据要写成区间，不是 0。
3. 任何新检查器必须先给出**一个已知错误版本会被判 FAIL** 的证据，否则它证明不了任何事。

## 4.9 按「屏幕亮区掩码」拟合四边（2026-10-18 第四次返工，这次有量化判据）

用户的反馈精确到方位，直接指出我错在哪：

> 镜头1、2、4、16：画面左侧和下侧与屏幕距离过大，上侧和右侧距离过小
> 镜头6、10、12、14：画面与镜头角度未对齐，且比之前都大

第一条 = **整体平移**；第二条 = **角度**。而 §4.8 里我把 3.98° 的角度修正回退掉了，
所以「比之前都大」。判断错第二次。

### 为什么之前的量法都偏向内侧

沿法线取亮度剖面找边缘，会同时受这些东西干扰：屏幕内侧暗角、边缘反光圈、
屏内文字笔画、窗外亮景。判据一错，拟合出的边就系统性偏内或偏向一侧。

### 现在：用掩码边界，不用亮度阈值

屏幕是一块**亮而均匀**的区域，边框是暗的。从四边形中心洪泛亮区得到掩码，
**掩码的边界就是屏幕边缘**——没有灰度阈值可调，屏内文字只是掩码内部的洞，
不影响边界。然后：

1. 取掩码边界点，按「离哪条边近」分组
2. 每组做总体最小二乘拟合直线 → 四条边线 → 两两求交得四角
3. 迭代 3 轮（边和角互相拉动），收敛判据 0.2px
4. 四条边**先平移成新直线再求交**，统一内收 5px —— 这就是那圈「窄而均匀的亮边」
   （直接在原端点上叠加会互相拉扯，收出来的形状不均匀）

拟合 RMS：`window-day` 0.30~2.94px、`dusk-study` 0.31~2.64px、`office-bright` 0.29~2.06px。
上/下两条边的 RMS 偏大是圆角处的弧点造成的，不影响直线部分。

### 角度修正量（这才是用户看到的「不平行」）

| 环境 | 上边角度差 | 其余三边 |
|---|---|---|

### `check-fit.py`：把用户的话直接写成判据

```
每条边缝宽 ∈ [−1.5, 10] px      —— 「距离很小」
max(gap) − min(gap) ≤ 5 px      —— 「四条边一样」
```
