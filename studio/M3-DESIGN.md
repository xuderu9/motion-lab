# M3 设计：分镜规划器（SRT → 镜头时间轴）

> 目标：**输入一份 SRT（+ 可选 mp3 时长）→ 输出一份能直接喂给 M1 渲染器的 ShotSpec 数组。**
> 这是「一周出片」的最后一块拼图：M1 有渲染器，M2 有 18 个版面，但没有分镜就是一堆零件。

---

## 1. 为什么这一步不能跳过

人工排 3 分钟片子（约 15 个镜头）要决定：每段讲到哪、用哪个版式、哪个变体、哪套主题、
强调文字放什么。这件事每次换文案都要重做一遍。**如果这件事不自动化，产线就只有一条片子。**

人类已确认的方式（HANDOFF §2）：**AI 读 SRT 自动分配版式，人类只审成片。**

---

## 2. 输入

```ts
type PlannerInput = {
  srt: { index: number; start: number; end: number; text: string }[];  // 秒
  audioDuration?: number;      // mp3 实测时长，用来核对 SRT 是否完整
  options: {
    targetShotSec: [number, number];   // 默认 [8, 16]
    minShots: number;                  // 默认 10
    seed: number;                      // 约束求解的可复现随机种子
  };
};
```

## 3. 输出

```ts
type Plan = {
  shots: ShotSpec[];        // 直接可渲染，env 由环境注册表填
  report: {
    totalSec: number;
    shotCount: number;
    layouts: Record<string, number>;    // 各版式用了几个
    themes: Record<string, number>;
    warnings: string[];                 // 派生内容里的"猜"的部分，人类要审
  };
};
```

---

## 4. 四步流水线

### 4.1 分段（segment）：SRT 行 → 镜头边界

**不要一行一个字幕一个镜头。** 参考片 161 秒只有 11 次硬切（平均镜头 14 秒）；
3 分钟片子按 8~16 秒切就是 12~22 个镜头。一行 3 秒切一个会有 60 个镜头，
既碎又没法让版面动起来（页面滚动需要时间）。

算法（贪心 + 打分）：

```
从第 0 行开始：
  累积行，直到满足任一条件就断：
    · 时长 ≥ targetShotSec[1]（硬上限，必须断）
    · 时长 ≥ targetShotSec[0] 且 断点分数最高
  断点分数 = 0.55·行尾标点权重 + 0.30·SRT 停顿长度 + 0.15·语义切换信号
    · 行尾标点：句号/问号/感叹号 = 1.0，逗号/顿号 = 0.3，无标点 = 0
    · 停顿：下一行 start - 本行 end，>0.4s 记 1.0，线性归一
    · 语义切换：本镜头内数字/日期/专有名词的密度与下一行差异（见 4.2 的特征）
```

断点必须落在**行边界**上——不允许切断一条字幕。这条是硬约束（验收第 2 条）。

### 4.2 版式打分（score）：这段在说什么

对每个镜头的全文做特征提取，给 6 个版式各打一个分：

| 特征 | 提取方式 | 偏向的版式 |
|---|---|---|
| 数字与百分号密度 | 正则 `\d+(\.\d+)?%?` | chart 强，cards 弱 |
| 年份/日期 | `\d{4}年|\d{1,2}月|\d{1,2}日|第\d+` | timeline 强 |
| 地名/地点词 | 词表 + `位于\|途径\|起点\|终点` | map 强 |
| 代码标识符形态 | `[a-z]+_[a-z]+`、`()`、`{}`、英文标识符密度 | code 强 |
| 枚举连词 | `第一\|第二\|首先\|其次\|另外\|还有` 计数 | cards 强 |
| 长句为主、无上述特征 | 兜底 | doc 默认 |

```ts
score = {
  chart:    2.0·numDensity + 0.5·enumCount,
  timeline: 2.5·dateCount + 0.3·numDensity,
  map:      2.5·placeCount,
  code:     2.5·codeDensity,
  cards:    1.8·enumCount + 0.4·numDensity,
  doc:      0.6,                       // 兜底分，永远可选项
}
```

**为什么用规则不用 LLM**：可复现、可测、零成本、能回归。
LLM 只在 M3.1 作为可选精修（`--refine` 参数），不阻塞主流程。
人类最终审成片，所以规则版够用。

### 4.3 约束求解（solve）：变体与主题怎么排

硬约束（违反任一即验收不过）：

1. 相邻两镜头**不得同 `layout`**（否则看起来没换场）
2. 相邻两镜头**不得同 `theme`**
3. 同一 `(layout, variant)` **间隔 ≥ 4 个镜头**（人类硬要求：不能看出是重播）
4. 同一 `theme` **不得连续出现 3 次**
5. 3 分钟片子至少用到 **4 个版式族**

软目标（加权惩罚，尽量满足）：

- 明暗节奏：亮主题连续 2 个之后，下一个优先暗主题（参考片就是明暗交替）
- 版式均匀：各版式出现次数尽量均衡
- 同族不同变体优先（同一版式的 3 个变体轮着用）

求解方法：**贪心 + 回溯**。逐镜头在合法集合里按软目标打分选最优；
无合法解就回退上一个镜头换选择（最多回退 3 层）。`seed` 固定时结果可复现。

**约束求解器必须自己先报告可行性**：如果 SRT 只有 3 个镜头，硬约束 1+2 就无解——
此时应该**明确报错**「镜头数不足，至少需要 N 个」，而不是偷偷放宽约束。

### 4.4 内容派生（derive）：把散文变成版面数据

每个版式要结构化数据（series、cards、outline…）。规则能抽到的抽，抽不到的记 warning：

| 版式 | 能确定性抽到的 | 抽不到时的兜底 |
|---|---|---|
| chart | 文本里的数字 → `series`（标签取数字前的 2~4 字）；百分比 → `metric.delta` | 用等差的占位序列，**记 warning** |
| timeline | 年份/月份 → 事件列表 | 用镜头内各行的先后当顺序，**记 warning** |
| map | 地名 → 地点列表；`起点/终点` → 航线 | 只画地点不做航线，**记 warning** |
| code | 反引号内或英文标识符 → 代码行 | 用一段通用示例代码，**记 warning** |
| cards | 枚举句 → 卡片标题+正文 | 按行拆成卡片，**记 warning** |
| doc | 镜头全文 → 段落；关键词 → outline | 直接用全文，**无 warning** |

**铁律：不许静默编造。** 派生失败一律进 `warnings`，人类审的时候看这一栏。
这条源自 M1 §6 陷阱 3（版式里不许硬编码文案）的延伸——规划器也不许假装知道。

### 4.5 强调层（overlay）怎么给

当前每个镜头都带 overlay 且 68% 处入场。**15 个镜头全弹字会很单调。**

规则：
- 只有**段落第一个镜头**给 overlay（kicker = 段名，title = 该镜头第一句的核心短语，bullets = 该段后续 2~3 个要点）
- 全片最后一个镜头给 overlay（人类明确喜欢末尾弹出）
- 其余镜头 `overlay` 留空

判据：3 分钟片子的 overlay 镜头占比应在 **20%~40%**。

## 5. 文件规划

```
studio/planner/
├─ types.ts        PlannerInput / Plan / 中间结构
├─ parse-srt.ts    SRT 解析（含 BOM、CRLF、多行字幕、时间码越界校验）
├─ features.ts     文本特征提取（数字/日期/地名/代码/枚举）
├─ segment.ts      4.1 分段
├─ score.ts        4.2 版式打分
├─ solve.ts        4.3 约束求解（贪心+回溯）
├─ derive.ts       4.4 各版式的内容派生
├─ environments.ts 环境注册表（读 studio/plates.json，给每个镜头分配 env）
└─ plan.ts         CLI：node --experimental-strip-types plan.ts --srt x.srt --out y.json
studio/plates.json 环境注册表：{ name: { src, quad, cornerRadius, exposure } }
studio/tools/check-plan.py   验收（见 §6）
```

`studio/plates.json` 是 M3 引入的新东西：4 个环境的名字 → env 参数。
规划器按软目标（镜头时长/版式）分配环境，人类改这一个文件就能换整片的环境基调。

## 6. 验收标准（先写，后做）

| # | 指标 | 判据 | 怎么测 |
|---|---|---|---|
| 1 | 时长闭合 | 所有镜头时长之和 = SRT 总时长 **±0.5s**，无空洞无重叠 | `check-plan.py` |
| 2 | 边界对齐 | 每个镜头边界都落在某条字幕的起/止点上（误差 0） | 同上 |
| 3 | 硬约束 | §4.3 的 5 条违规数 = **0** | 同上 |
| 4 | 版式覆盖 | 使用的版式族 **≥4**，且每个族内变体 ≥2 种 | 同上 |
| 5 | 不静默编造 | 每个镜头的每个字段都非空；派生失败的都在 `warnings` 里 | 同上 |
| 6 | 一条命令 | CLI 跑一次出 `plan.json`，直接 `render-batch.ps1` 能吃 | 端到端 |
| 7 | 换本跑通 | 换一份没见过的 SRT，无人值守出片成功 | 端到端 |
| 8 | 可复现 | 同一 `seed` 跑两次，`plan.json` 字节级相同 | diff |

第 8 条容易被忽略但很重要：分镜不可复现，就没法「只改文案看差异」。

## 7. 三个必须避开的陷阱

1. **不要把「一行字幕」当「一个镜头」。**
   3 分钟 60 行字幕，1:1 切会得到 60 个 3 秒镜头，版式的页面滚动、图表呼吸全都来不及发挥，
   而且帧差指标会假性通过（每次切换都是一次大变化）。参考片平均镜头 14 秒。

2. **不要在求解器里偷偷放宽约束。**
   无解就是无解（镜头太少 / 版式太少）。宁可报错让人加内容，也不要输出一个违反约束的方案——
   那种片子看起来「像重播」，而且是静默的，人类看不出来是规划器的锅。

3. **不要让派生内容假装是真的。**
   文本里没有数字却画出一条像样的折线，观众会觉得「这数据哪来的」。
   宁可画占位并标 warning，也不要伪造。

---

## 8. 与 M1/M2 的接口

- 输出**严格**是 M1 的 `ShotSpec`（`validateSpec` 必须能过）
- `env` 从 `studio/plates.json` 取，不在规划器里硬编码
- `content.kind` 必须等于 `layout`
- 字号/颜色/动效一律不碰——那是版式的事

## 9. 范围与顺序

**M3 交付**：解析、分段、打分、求解、derive（6 个版式的全部）、environments、check-plan。
**不做**：转场（M4）、字幕烧录（M5）、性能（M6）。

顺序：
1. `parse-srt.ts` + `features.ts`（能打印每行特征）
2. `segment.ts`（对着真 SRT 打印分段结果，人工看一遍是否合理）
3. `score.ts` + `solve.ts`（打印规划表 + 约束违规数）
4. `derive.ts`（逐版式补，先 chart/doc 这两个最常用的）
5. `plan.ts` CLI + `check-plan.py`
6. 跑验收，对着真 SRT 出一份 plan，渲出第一条端到端片子

## 10. 写实现时发现的规则问题（已修正，别再犯回去）

在 `studio/shots/sample.srt`（40 行 / 175 秒）上跑第一版，分布是 `chart: 13, cards: 1, doc: 3, code: 1`。
四个问题，全部已修：

### 10.1 中文数字是隐形的
第一版只认阿拉伯数字，于是「二十分钟 / 三十个文件 / 十几处代码」全部漏判，
这一段本该是 chart 却掉进 doc。补了中文数字形态 + `chineseToNumber()`（二十/十五/两千/十几）。

### 10.2 序数被当成数据
`第[一二三四五六七八九十]+` 既是枚举（cards 的信号）又被数字正则吃到（chart 的信号）。
「第二个代价 / 第三次转移」让 chart 的分数在 18 个镜头里抢走 13 个。
修法：数字正则加 `(?<!第)` 负向后顾。

### 10.3 密度必须封顶
一段话里数字越密集 chart 分越高，没有上限 → 数字密集段直接碾压。
封顶之后：`numDensity ≤ 3`、`codeDensity ≤ 3`、`enumCount ≤ 6`。

### 10.4 候选集必须永远包含 doc
只给「得分 ≥ 最佳值 80%」的候选，在很多镜头上只剩一个选择，
约束求解器必然无解（相邻不能同版式）。
**doc 能把任意散文渲染成阅读页，所以它永远是合法候选**；其它版式需要能派生出结构才行。

### 10.5 尚未解决
纯规则打分对「修辞性数字」仍然不敏感：
「三次范式转移之后我们得到了什么」里的「三次」是修辞不是数据，却拿到 chart 的分。
目前靠约束求解器兜底（chart 不能连用、必须 ≥4 个族）。
如果实测下来还是偏，再考虑 `--refine` 调 LLM 精修，而不是继续加规则。
